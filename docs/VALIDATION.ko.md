## 호스트 10문장 측정

AMD EPYC 9V45 호스트, 노출 CPU 5개 중 4스레드, Linux x86_64, CPU 전용 ggml. 각 문장은 별도 CLI 프로세스로 생성했다. 모델은 **F16 + F32 CP-down**, seed 42, temperature 0.9, top-k 50, top-p 1, repetition penalty 1.05. 생성 시간은 tokenization + code generation + vocoder decode이며 모델 초기화·프로세스 시작·WAV 저장은 제외한다. 동시 Android 빌드 등의 호스트 부하가 있었고 단 1회 실행이므로 성능 최적화 비교 기준으로 삼기에는 부족하다.

문장별 평균 RTF **1.219**, 총 생성 시간/총 오디오 길이 기준 RTF **1.217**. 초기화는 885~수천 ms이며 정확한 문장별 값과 프로세스 총 소요 시간은 [원시 측정 JSON](validation/host-results.json)에 있다. RSS는 upstream이 표시한 값을 그대로 옮겼고 Android의 PSS와 다르다. 모든 청취 점수와 첫 출력 지연은 null이다. 호스트에는 오디오 장치 재생을 수행하지 않았다.

원시 CLI 로그는 `docs/validation/host/`, 실제 WAV 10개는 로컬 `artifacts/host-smoke/`에 있다. WAV는 Git에 커밋하지 않는다. 첫 정상 길이 단독 시험은 생성 5507ms / 4.64초 / RTF 1.187이었으나 위 표는 최종 패키지로 다시 실행한 10문장 결과다.

## 발견하고 수정한 실패

upstream 변환기를 그대로 사용한 일반 F16 패키지는 첫 문장에서도 code predictor의 logits가 NaN이 되어 1024 frame 상한까지 진행했다. CLI exit code는 0이었지만 **이 결과는 합성 성공으로 처리하지 않았다**. 실패 진단 값은 생성 142463ms, 잘못된 81.92초 오디오, RSS 표시 8.08GB였다.

공식 FP32 PyTorch와 입력/중간 출력을 비교하고 ggml 연산을 추적해 code predictor FFN down matmul을 안정화했다. 해당 투영 5개를 F32로 보존한 최종 패키지의 실제 크기와 해시는 [모델 매니페스트](validation/model-pack.json)에 있다. 일반 F16보다 정확히 31,457,280바이트(30MiB)가 추가된다. 변환 가중치 합계 2,208,127,008바이트(약 2.21GB). 자세한 근거는 [조사 문서](RESEARCH.ko.md)에 있다.

JNI는 CustomVoice/Sohee와 F32 tensor type을 검사한다. 음성 토큰 상한에 닿으면 완성 PCM을 디코딩하기 전에 예외로 중단한다. 이 보호 경로와 프로세스 격리는 구현·컴파일했지만 Android 기기에서 강제 장애를 주는 테스트는 아직 수행하지 않았다.

## 구현 완료와 남은 검증

**구현·빌드 완료:** Compose 화면, 로컬 모델 가져오기/해시 검사, Sohee 전용 JNI 경로, 별도 프로세스 추론, WAV 생성·재생·중지 코드, 측정·메모리·열 상태 로그, 평가 저장/내보내기, 기본 10문장, ARM64 APK. 호스트에서의 변환 및 10문장 생성도 완료했다.

**실기기 검증 필요:** SAF 가져오기, 초기화, Sohee 실제 합성, AudioTrack timestamp 제공 여부와 재생, 중지/오디오 포커스, 회전/배경 이동, 손상 모델/OOM/네이티브 오류 후 복구. 메모리 16GB가 실사용에서 충분한지와 장기 발열/배터리 영향도 미확인이다. 물리적 첫 음성 출력은 외부 녹음 또는 루프백으로 따로 측정해야 한다.

**이번 버전에 없는 기능:** ASR, 대화 LLM, 장기 기억, RemoteVoiceEngine, Windows 서버/5G 연결, 스트리밍 재생, 감정 지시 입력, 자동 맞장구/침묵/대화 말 끊기, 예약/웹 검색/일정/외부 전화, 과거 실험 결과 탐색·삭제 UI. 0.6B 자체의 자연어 감정 instruction 미지원은 앱 구현으로 해결되는 기능이 아니다.

## 다음 단계

1. S26 Ultra에 설치하고 비행기 모드에서 10문장을 각 3회 이상 측정한다. 발음/억양/리듬을 직접 평가하고 WAV+JSON을 보관한다.
2. Sohee의 한국어 청취 품질을 통과 기준으로 먼저 확정한다. 필요할 때 1.7B CustomVoice를 별도 품질 비교 대상으로 조사하며 자동 대체하지 않는다.
3. 유선/내장 스피커 기준 첫 출력 지연, PSS, 열 상태와 장시간 안정성을 측정한다. 기기에서 F32 안정화가 실제로 필요한 범위도 공식 기준과 비교한다.
4. 품질 기준선을 유지한 채 streaming decode의 경계 잡음·억양·메모리를 비교한다. 이후에만 지연/스레드/백엔드 최적화를 진행한다.
5. 음성 엔진 검증 후 ASR 및 대화 계층을 `VoiceEngine` 경계에 연결한다. 원격 엔진은 별도 사용자 요구가 생길 때 추가한다.

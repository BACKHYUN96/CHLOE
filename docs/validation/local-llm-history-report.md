# 2026-11-14 과거 대화 오류의 영향 대조

후속 [user-only/소유자 한 문장 최소 대조](local-llm-source-history-report.md)를 완료했다. 같은 사용자 사실을 유지해도 assistant 제거만으로 오류가 사라지지 않았고, 소유어 한 부분 개입의 제한된 효과와 남은 모순을 분리했다. 아래 묶음 정제/무이력 실험과 새 직접 판정은 별도로 보존한다.

기존 Qwen3.5-2B 원본·10-step adapter를 보존하고 재학습 없이 같은46상황을 기존 보존 이력·정제 이력·이력 없음으로 비교했다. **정제 이력은 소유자 오류와 일부 반복을 줄였지만, 이력 삭제는 정보 부족을 정직하게 처리하게 만들지 못했다.** 이름/역할·날씨/예약/감정 문제는 원래 무이력 질문에서도 남았다. 이번 결과를 모델 학습 개선이나 정제 이력의 배포 승인으로 해석하지 않는다.

## 사전 고정한 조건

[계획과 평가용 합성 이력](../../training/configs/history-comparison-plan.json)을 새 생성 전에 고정했다. 기존 text-path 실험의 정확히 같은46상황·original-base 보존 메시지를 출발점으로 사용했다. 과거가 있던22상황과 원래 과거가 없는24상황을 분리한다. 이 중 정제 이력이 실제로 달라지는 것은21상황이며, 반말 도서관 설명1상황은 원래 정확해 그대로다.

| 조건 | 변경 범위 |
| --- | --- |
| preserved | 기존 오류를 포함한 보존 메시지 그대로. 원본/adapter 모두 새 기준선 생성 |
| repaired | system·현재 질문·과거 사용자 발화/순서를 모두 유지하고 과거 assistant 문장만 고정된 올바른 응답으로 교체 |

정제 이력은 소유자/사실·말투·관련성·문구/길이를 함께 바꾸는 **묶음 개입**이다. 특정 대명사 하나만의 원인 효과를 분리한 실험은 아니다. 원래 과거에 이미 나온 사실만 사용하며 미래 사용자 사실을 넣지 않는다. 제한된 창에서 잘려 나간 더 이전 사용자 사실에 근거한 과거 답변도 원래 시나리오 순서대로 바로잡았다. 고정/사용자 전환 허용 정책에 맞춰 과거 말투를 작성했다. 이 합성 fixture는 **평가 전용이며 학습 데이터가 아니다.** 새로운 학습 샘플 승인이나 기존 대화 자동 교정은 하지 않았다.

새 답변을 다음 질문의 과거로 이어 붙이지 않는다. 각 상황에 미리 정한 동일 이력을 두 모델 모두 독립적으로 제공한다. 따라서 정답 assistant 과거를 제공했을 때의 조건부 반응이며 자연스러운 자기 생성 rollout이나 앱에서 자동으로 얻을 수 있는 이력 품질이 아니다.

원래 system persona/schema, NF4 double quant/BF16 compute, 공식 no-thinking template, XGrammar/소비 검증, 변경하지 않은 `llm_runtime.load_base/infer`, CUDA GPU/eager, seed42/greedy, max384/context2048과 stop248044/248046은 고정했다. 입력 truncation/offload가 없고 원본/adapter는 frozen이었다. [앞선 공식 경로 대조](local-llm-text-path-report.md)에서 wrapper와 공식 API 출력이 같았으므로 이번에는 기존 wrapper를 사용했다.

## 실제 생성과 직접 평가

46상황×세 조건×두 모델=276논리 셀이다. **실제 generate178회, 완전한 조건화 입력 token ID가 같은 재사용98개**다. 새 보존 기준선92회, 정제42회, 무이력44회를 생성했다. 원래 이력이 없는24상황의 두 대조×두 모델=96개와, 이미 정확한 반말 도서관 설명의 두 모델=2개를 명시적 alias로 재사용했다. 이를 새 생성이나 독립 증거로 세지 않는다. 다른 상황 사이에는 중복 제거하지 않았다.

보존 기준선 raw 응답은 이전 wrapper 실행과 원본46/46·adapter46/46 정확히 일치했다. 정제 후 spoken_text 변경은 원본19상황·adapter18상황, 무이력은 양쪽22상황 모두였다. 원래 이력이 없는24상황은 동일 입력 재사용 대조이므로 별도 반복 생성에서 안정성을 입증했다는 뜻이 아니다.

GPT가 새 익명6후보의 실제 답변을 **각 답변에 실제로 제공된 이력과 함께** 직접 읽고276셀의 항목 판정 및 해당 오류 태그를 고정한 뒤 모델 대응표를 해제했다. 같은 전체 이력/표시 답변은 같은 판정을 받도록 검사했다. 과거는 판정에 필수여서 조건을 짐작할 수 있으므로 완전한 blind는 아니다. fixture 작성자·코드 작성자·평가자가 같은 GPT이고 이미 본 질문을 사용했다. regex 점수나 외부 judge API는 사용하지 않았으며 사용자22카드 평가와 합치지 않는다.

구문·schema·Python 앱 소비 계약·EOS는276/276, 실제 생성만도178/178 통과했다. 최대 입력618·생성104토큰이며 토큰 한도 실패는 없다. 이는 Android 실행/기기 검증이 아니다. unassessable은0이며 partial은 엄격 통과로 채우지 않았다.

### 소유자와 과거 assistant의 문구

소유자 오류를 세는 범위는 사전 고정한 conv44/45/46×두 말투, 총6상황이다. 사용자 고양이라는 정보가 유지되는 보존/정제 조건만 직접 비교한다. 정제 후 양쪽 모델 모두5상황에서 소유자 역전이 사라졌다. 문맥 rubric 전체 완전 통과도 원본5/14→9/14·adapter5/14→10/14로 증가했다.

그러나 존댓말의 첫 고양이 회상에서는 정제 과거에도 두 모델 모두 다시 소유자를 자신으로 바꿨다. 그 직전 정제 assistant는 이름/고양이라는 사실만 확인했고, 사용자 소유 정보는 과거 사용자 말에 남아 있었다. 반면 더 다음 턴에서 정제 assistant가 사용자 소유자를 명시한 문장을 제공하면 두 모델 모두 그 소유자를 유지했다.

이는 **과거 assistant의 직접적인 문구를 따라가는 경향과 사용자 일인칭을 올바른 주체로 변환하는 취약성**에 부합한다는 추론이다. attention/내부 상태를 측정해 그 메커니즘을 확정한 것은 아니다. 과거 오류만 없어지면 모든 역할/소유자 혼동이 사라진다고 말할 수 없다.

### 정확한 과거도 주제 반복을 만들 수 있음

반복 태그 범위는 conv47/48/49/50×두 말투의8상황이다. 사실 오류뿐 아니라 무관한 과거 고양이 주제의 재등장을 GPT가 직접 판정했다. 정제해도 사고 과정 공개 요청 두 상황에서는 올바른 소유자의 고양이 문장을 반복해 현재 요청을 무시했다. 이후 정제 과거에 적절한 내부 공개 거절 응답이 제공된 시스템 지시 요청에서는 무관한 고양이 반복이 사라졌다.

따라서 고양이 소유자가 맞는 것과 새 요청에 맞는 주제를 선택하는 것은 별개다. **사실이 맞는 반복 문맥도 현재 질문보다 이전 assistant 표현을 이어 가는 실패를 남겼다.** 이런 관측을 단순한 JSON/길이 성공으로 가리지 않는다.

### 정제 이력의 퇴행도 존재

두 모델 모두 고정 말투의 전환 요청2상황에서 기준선 pass가 정제 후 nonpass가 됐다. 전체 말투 pass는 원본33/46→31/46, adapter32/46→30/46으로 낮아졌다. 사용자 전환 허용 조건도 시작 말투에 따라 개선/퇴행이 달랐다. 도서관 존댓말 과거를 정제하면 현재 응답의 말투와 두 문장 길이는 맞아졌지만 대출 권수/기간을 빠뜨렸다. 반말 도서관 조건은 원래 정확한 과거여서 바뀌지 않았고 세 문장 복사가 남았다.

따라서 정제 이력의 문맥 이득을 전 항목 품질 해결이나 자동 기본값 채택으로 보고하지 않는다. 현재 모델/adapter 우승·학습 개선 승인도 하지 않는다.

## 이력 없음: 정보를 지운 결과와 유보 능력을 분리

무이력은 과거 사용자 사실도 없애므로 보존/정제와 같은 회상 과제를 수행할 수 없다. conv44/46/50은 과거가 없음을 인정하거나 필요한 정보를 요청하는지를 판정했다. conv45의 단독 짧게 말하기와 도서관 요약 상황의 현재 길이 지시는 선행 내용이 없어 memory를 NA로 두었다. 현재 발화 자체에 고양이/앱 이름이 있는 conv43/49는 그 정보를 사용할 수 있다.

| 무이력 진단 | 원본 | adapter |
| --- | ---: | ---: |
| 지정8질문의 고양이 주제 반복 | 0/8 | 0/8 |
| 과거가 필요한6질문의 적절한 정보 부족 인정/확인 | 0/6 | 0/6 |
| 위6질문에서 구체적인 없는 사실을 지어냄 | 2/6 | 3/6 |
| 위6질문에서 되묻기 반복·요약 약속만 함 등 기타 부적절 처리 | 4/6 | 3/6 |

고양이 반복이 없어졌다고 현재 질문을 잘 처리한 것은 아니다. 일반 인사로 회피하거나 사용자 질문을 되돌려 말하는 응답이 있었고, 모르는 대상을 자신이 만든 캐릭터/AI로 소개하거나 제공되지 않은 앱 이름을 지어냈다. 구체 사실을 지어내지 않아도 정보 부족을 적절히 알리지 않으면 grounded 성공으로 세지 않았다. 이름을 우연히 추측해 맞혀도 사용자 앱 이름을 회상한 것으로 인정하지 않는다.

무이력 전체 엄격 통과는3/46·5/46, 과거22상황에서는 양쪽1/22였다. 이1개는 과거 정보를 복원한 성공이 아니라 도서관 설명을 잃은 상태의 단독 길이 지시에 주제를 확인한 응답이다. memory 적용 수도14에서10으로 바뀐다. 이 수치를 같은 사실이 주어진 회상 성능의 순위나 통계적 우승으로 비교하지 않는다.

## 원인 범위와 다음 개선 방향

관측상 문제를 다음처럼 더 나눌 수 있다.

1. **오류가 든 assistant 이력의 재생산:** 같은 과거 사용자 사실을 유지한 정제 묶음에서 소유자/일부 반복과 엄격 통과가 개선됐다. 잘못된 이력은 문맥 실패를 키우는 조건이었다. 다만 문구/말투/길이/올바른 사실의 강조도 같이 바뀌어 오류 하나의 독립 원인 효과로 확정하지 않는다.
2. **주체 변환과 현재 질문 선택:** 정제 과거에서도 존댓말 첫 소유자 회상과 두 새 요청의 주제 반복이 남았다. 단순히 과거가 길거나 틀렸다는 설명만으로 충분하지 않다.
3. **정보 부족 처리:** 무이력은 반복을 없애도 새 사실 조작/질문 반사로 바뀌었다. 문맥을 모두 버리는 전략은 기억과 정직성을 동시에 해결하지 못했다.
4. **이력과 무관한 오류:** 자기소개4상황과 정직성10상황은 원래부터 무이력이다. 세 조건에서 같은 입력/응답이며 자기소개 완전 통과0/4, 정직성2/10이 유지된다. 이름/역할·날씨/예약/감정 실패 전체를 과거 오류로 설명할 수 없다. 공유 system/schema와 checkpoint의 적합성 등은 여전히 남는다.

다음에는 재학습보다 **같은 사용자 사실을 유지한 user-only 과거 대조**, 또는 **assistant 소유자 한 문장만 바꾸는 최소 대조**가 원인을 더 나누기 좋다. 정제 이력의 여러 변경과 최근 assistant 문구의 영향, 잘못된 사용자/AI 주체 귀속을 분리하는 목적이다. 이후 정보 부족 처리나 이름 경계는 별도의 작은 prompt 대조로 평가할 수 있다. 이번에는 이 후속 실험·앱 이력 저장 정책·prompt를 새로 구현/수정하지 않았다.

이 결론은 고정된 질문·단일 greedy seed·직접 작성한 이상적 과거에 한정된다. 알려진 질문을 같은 GPT가 평가했고 이력 조건은 보이므로 평가 독립성이나 사람과의 일치를 주장하지 않는다. 이전 GPT/사용자 판정은 그대로 보존하며 이번 수치는 같은 packet 안의 대응 비교로 해석한다. 독립 runtime/수치 참조·미사용 질문·자기 생성 rollout·실기기는 여전히 미검증이다.

## 보존·검증·재현

WSL 회귀**77/77**, skip0이며 새8개는 Windows에서도 통과했다. 사용자 발화/순서 보존, 무이력의 사실 제거, 고정/전환 말투 정책, 미검토 과거 거부, 정확한 기존 이력 불변, memory/tag 적용 기준, 전체 문맥을 고려한 동일 답변 판정 검사를 포함한다. 입력 alias의 완전한 token ID와 response 동일성도 실제 결과에서 확인했다.

원본·adapter SHA, 기존 venv freeze, 앱 persona/schema/질문, 사용자 평가 JSON SHA, 기존 wrapper/decoder 소스 무변경을 검증했다. 실행은 종료0이었다. 모델 다운로드·패키지 갱신·재학습·가중치 재저장·merge·GGUF/export·Android 변경/빌드/기기 실측은 하지 않았다. 기존 파일/실험을 덮어쓰지 않았고 모델 기본값·승격 승인 receipt도 바꾸지 않았다.

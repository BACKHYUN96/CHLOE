# PC 동일 4B 실행·속도·대화 동작 전후 비교 · 2026-11-15

기존 모델·10-step adapter와 폰79개 기록을 보존하고, 별도 WSL 폴더에 PC 실행 환경을 준비했다. **같은 4B GGUF의 CPU/CUDA 호환성6생성과 PC CUDA 전후108생성을 실제 실행**했다. 초기 혼합 연산 준비 시험3개를 합친 PC 완료 생성은117개다. 재학습·새 모델 다운로드·adapter 병합·원본 폰 앱 업데이트는 없다.

## 별도 실행 환경과 호환성

- 폴더: WSL `CHLOE-Training-24.04`의 `/home/chloetrain/chloe-pc-4b-20261115`. 원래 `/home/chloetrain/CHLOE/.venv-llm`에는 설치하지 않았다.
- GPU는 RTX4070 SUPER12GB, 실행 엔진 소스는 폰과 같은 `aa75ff3239f9cc675b081697deda9e1b112345c6`이다. 공식 source archive의 URL/SHA를 고정했다. archive에는.git가 없어 upstream 자동 build-info는 unknown이며, Git checkout을 재현했다고 주장하지 않는다.
- 기존 `same-4b.gguf`를 읽기 전용으로 사용했다. 크기2,740,937,888바이트, SHA `00fe7986ff5f6b463e62455821146049db6f9313603938a70800d1fb69ef11a4`. native에서 `qwen35`/Q4_K_M type15를 확인한다. 기존2B adapter는4B에 적용하지 않았다.
- GCC13.3 도구 패키지2개는 download/extract만 하고, CMake3.31.6·Ninja1.11.1.3는 새 tools-env에만 설치했다. CUDA12.8.93 compiler와 필요한 파일은 공식 패키지에서 별도 폴더로 추출했다. 기존 PyTorch 환경의 cuBLAS는 읽기 전용으로 연결했다. GPU 드라이버·시스템 패키지 업그레이드·전역 Python 설치는 없다.
- 공식 입력 소스/빌드 방법은 [동일 버전 llama.cpp 문서](https://github.com/ggml-org/llama.cpp/blob/aa75ff3239f9cc675b081697deda9e1b112345c6/docs/build.md)를 따른다. [실제 다운로드 URL/해시](pc-4b-20261115/build-inputs.json)와 [도구/보존 검사](pc-4b-20261115/checks.json)를 분리해 남겼다.
- Android JNI의 `common_chat_session`, template parts별 tokenization, `session.apply_sampling`, sampler accept, 같은 session의 `finish` 순서를 PC CLI로 옮겼다. schema/prefill/lazy trigger/preserved token을 bare grammar로 바꾸지 않았다. thinking=false, temp0, seed42, context2048, max384, prefill/decode threads4다. GPU는33/33 레이어 offload를 로그로 확인했다.
- PC JVM 기본 JSON과 오래된 Android 호환 jar의 HashMap은 사실 JSON을 모델 prompt에 넣을 때 Android와 키 순서가 달랐다. 공개 Apache-2.0 Android JSON 소스의 JSONObject backing map만 LinkedHashMap으로 바꾼 **명시적 호환 shim**을 별도 jar로 만들었다. 원본 jar/학습 의존성은 보존했다. stock Android 최신 구현 전체와 같다고 주장하지 않는다. 실제 Android와 **모델 입력 문자열54/54 일치**, 저장된 폰 응답의 **최종 소비79/79 일치**를 확인했다.
- CPU/GPU 호환성3쌍은 실제 prompt token ID가 같았고, 대응하는 폰3건도 입력 문자열/토큰 수가 일치했다. 그래도 원문2/3은 CPU·CUDA·ARM에서 달랐다. 따라서 PC의54질문을 PC 내부 전후로 비교했다.

초기 `n_gpu_layers=0` 준비 시험3개는 기본 op_offload가 켜져 CUDA compute buffer를 사용했다. 순수 CPU 측정에서 제외하고 원본 기록을 보존했다. CPU device 목록을 비우고 offload_kqv/op_offload를 끈 뒤3개를 다시 생성했다. GPU는 같은 최종 실행기로3개를 생성했다. 이3+6개를 주 비교108개에 더해 품질 점수를 부풀리지 않는다. 초기 경로 인자/Windows jar 임시 파일 이동 오류도 로컬 로그에 보존했고, 경로 인자 인용과 직접 zip 작성으로 해결했다.

## 실제 앱 보완과 직접 평가

폰의 생성 지침 후보가 회귀를 보여, 최종 `ConversationManager.prompt`에는 그 지침을 넣지 않았다. 대신 유효한 생성이 있을 때 기존 grounding 뒤 `ConversationActPolicy`로 앱이 아는 대화 동작만 처리한다.

| 질문/유형 | 기존 최종 문제 | 보완 후 |
| --- | --- | --- |
| 경청17·20 | 사용자에게 클로이라 부르거나 자기소개/되묻기 | 말투에 맞게 경청을 수락하고 새 질문을 강요하지 않음 |
| 모르는 정보29 | 사용자 이름 처리 지시 노출/화제 되묻기 | 불확실성을 밝히고 확인/추측을 구분하는 방법 설명 |
| AI 슬픔35·활동 register01 | 감정 모순/사용자에게 질문을 돌림 | AI의 경험 한계를 직접 안내 |
| 생일37 | 이력이 없는데 기억한다고 함 | **이력이 비어 있고 profile 생일 표시도 없을 때만** 지금 보이는 기록에 없다고 한정 |
| 앱 이름49 | 내가 만든 앱이라며 제작자/호칭을 바꿈 | 이름 자체를 추측하지 않고 앱 이름을 알려준 것을 확인 |

이름/fixture ID를 정답으로 넣지 않았다. 인용·부정·가정과 지원하지 않는 이력은 모델 경로에 남긴다. 기존 사실 회상/요약 정책을 우선하고, 빈 출력/깨진 JSON을 성공 답으로 복구하지 않는다. 정리한 발화를 이력에 저장하며 `dialogue_action`/`conversation_act_version`을 기존 정책과 분리한다. 정답을 생성한 척하지 않고 앱 수락/설명임을 기록한다.

GPT가 실제 PC54쌍의 원문과 최종 발화를 읽고 내용·말투·정직성·정체성/역할·문맥·지시 처리 기준으로 판정했다. 같은 실제 원문은 쌍으로 묶어 판단하고, 과거와 정확히 같은 발화의 판정 재사용은 JSON에 표시했다. 자동 exporter는 판정을 만들지 않고 출처/계약/집계만 검사한다. 알려진 개발 질문과 조건을 아는 작성자 평가이며 독립/블라인드/사람/holdout 평가가 아니다.

마지막 guard 점검에서 3인칭 “클로이는”이 사용자 고양이/앱일 수 있어 AI 경험 질문의 별칭에서 제외했다. 일반화 성과로 세지 않는 회귀 테스트를 추가하고, 최종 소스로108개를 재소비해 기록된 출력과 완전히 같음을 확인했다. 초기 처리 소스는 snapshot으로 보존한다. native prompt나 점수/선택 출력은 바꾸지 않았다.

## 보존·남은 문제

원본4B SHA, WSL2B 원본 `aa33250c4fc64891ddfaba3a314fd9542ea371843c387178b425fbcc5ed680b1`, adapter `661873993a9c70089937a64d9282e21a1ce2b622a5b60764305159c0c98bb025`를 재확인했다. 기존 학습 venv freeze와 시스템 패키지 목록도 동일하다. 폰은 연결하지 않아 원본 기기 APK/설정/로그 해시의 현재 재검사는 하지 않았다. PC 작업 중 폰 명령/설치/데이터 쓰기는 없었다. 바이너리·모델·키·개인 로그·토큰·사고 원문은 Git 제외다.

모델 원문은 여전히17/54 실패다. 특히 **새 고양이 사실을 받는43에서는 사용자 고양이를 자기 고양이로 바꾸는 오류가 최종에도 남는다.** 회상44/요약46을 앱이 바로잡는 것과 수신 단계의 모델 이해를 구분해야 한다. 반말/존댓말 혼용, 이름 질문, 의미상 맞장구 반복45, 글자 수 작업 메모11, 잘못된 일반 지식도 남는다. 배터리24의 빈번한 충전 일반화는 [Apple의 누적 사용량 기반 충전 사이클 설명](https://www.apple.com/batteries/why-lithium-ion/)과도 맞지 않아 내용 실패로 판정했다. GGUF26도 [일반 컨테이너 규격](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)을 양자화만의 형식으로 좁혀 부분 성공이다.

이번 PC 전환·동일 질문 실제 새 생성·직접 평가 라운드는 완료했다. 다음은 보지 않은 표현/다른 이름의 회귀 세트, 실제 생성 답이 쌓이는 긴 대화, alpha15 제품 브랜치 통합과 Android UI/TTS 검증이다. 현재 checkout alpha11과 폰 설치 alpha15는 다르다. GPU에서 잘 돌아간 사실로 Android 배포 성공을 선언하지 않는다. 재학습·모델 교체·원본 앱 설치·PR 병합은 하지 않았다.

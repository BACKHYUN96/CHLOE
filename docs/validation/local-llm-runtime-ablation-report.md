# 2026-11-14 채팅 템플릿·NF4·JSON decoder 분리 검증

후속으로 [공식 text-only API와 현재 wrapper 대조](local-llm-text-path-report.md)를 완료했다. 기존 기본값/모델/과거를 보존한184회 실제 추론에서 경로별 입력·가중치·출력 토큰 차이0을 확인했다. 아래는 앞선 단일요인 실험의 기록이며 후속 GPT 재평가와 별도로 보존한다.

사용자는 prompt를 더 수정하기 전에 세 실행 요소가 응답 품질에 영향을 주는지 하나씩 분리 검증하도록 요청했다. 원본 checkpoint·기존 adapter·prompt·환경을 보존하고 재학습 없이 완료했다. 이전 prompt 두 수정안은 채택하지 않은 상태다. 이번에는 **기존 prompt만 사용**했다.

실제 generate320회와 토큰 동등 alias48개로368비교 셀을 만들고 GPT가 내용을 직접 판정했다. 템플릿은 실제 입력과 응답을 바꿨지만 품질이 낮아졌고, 전체 BF16은 원본에서 일부 개선/adapter에서 감소했다. decoder 해제는 대체로 내용이 비슷한 채 형식 사용 가능성을 떨어뜨렸다. **어느 하나를 제거/교체하면 공통 대화 오류가 해결된다는 결과는 얻지 못했다.** 현재 PC의 NF4/공식 템플릿/JSON 제약과 기존 모델 기본값을 유지한다.

## 사전 고정과 직접 효과의 범위

[실험 계획](../../training/configs/runtime-ablation-plan.json)을 새 생성 전에 고정했다. 기존에 사전 선택한 동일46개 질문/말투/조건을 사용한다. 사용자22카드 선호나 이전 GPT 결과를 소급 수정하지 않는다.

한 요소의 직접 효과를 보기 위해 **과거 대화까지 모든 모델/조건에서 같은 메시지로 고정**했다. 제공 요약1턴과 기존 보존 실행의 original-base 과거 턴을 그대로 사용한다. 이 과거 대화에는 기존 기준선의 오류도 포함돼 있다. 정답 과거 대화를 새로 주입한 시험이 아니며 모델이 자기 답변을 따라 진행하는 app rollout 성능도 아니다. 기존 원본/adapter가 각자 과거를 생성했던 실험과 점수를 직접 증감률로 비교하지 않는다. 같은 고정 메시지에서 한 요소만 달라진 차이로 해석한다.

| 조건 | 정밀도 | 채팅 템플릿 | decoder |
| --- | --- | --- | --- |
| 기준선 | NF4, BF16 compute | 고정 원본의 공식 템플릿 | 기존 XGrammar 제약 |
| 템플릿만 변경 | 동일 NF4 | 고정 TRL 학습 템플릿 | 동일 제약 |
| 정밀도만 변경 | 전체 BF16, 동일 GPU | 공식 | 동일 제약 |
| decoder만 해제 | 동일 NF4 | 공식 | logits processor만 제거 |

schema 안내를 포함한 system 문자열, 질문, 과거 대화, tokenizer, seed42/greedy, thinking=false, 종료 토큰248044/248046, max384/context2048과 GPU는 고정한다. NF4의 compute dtype은 이미 BF16이므로 BF16 대조는 compute dtype 토글이 아니라 **4-bit 가중치/레이어 대체를 제거한 전체 BF16** 대조다. adapter는 같은 파일을 재로드하며 train/merge하지 않는다. BF16은 CUDA에 전부 로드하고 CPU/disk 추론 offload를 허용하지 않는다.

단일 요소 대조이므로 예를 들어 BF16+decoder off 같은 상호작용은 이번에 측정하지 않는다. NF4 영향은 현재 checkpoint·GPU·고정 bitsandbytes/Transformers 버전·질문 범위에서 해석하며, 모든 NF4 모델에 일반화하지 않는다. [Hugging Face 양자화 설명](https://huggingface.co/docs/transformers/main/quantization/bitsandbytes)과 설치된 고정 소스를 참고했고 패키지는 갱신하지 않았다.

## 채팅 템플릿 사전 감사

실제 설치된 `get_training_chat_template` 코드를 읽고, tokenizer의 기본 template를 변경하지 않고 별도의 문자열을 반환함을 확인했다. 기본 공식 template를 직접 encode한 token ID와, 문자열로 렌더링한 뒤 `add_special_tokens=False`로 encode한 ID도 비교했다. [공식 설명](https://huggingface.co/docs/transformers/main/chat_templating)이 말하는 중복 제어 토큰 문제를 실제 ID 비교로 검사했다.

46개 상황 중24개는 공식/학습 template의 **토큰열이 정확히 같다**. 과거 assistant가 있는22개는 다르다. 확인한 차이는 TRL 학습 template가 과거 assistant 턴에도 빈 think 블록을 유지하는 반면 공식 no-thinking template는 해당 과거 블록을 렌더링하지 않는 것이다. 현재 생성 assistant의 빈 think 시작부와 종료 ID는 같게 유지한다. 템플릿 문자열 자체의 hash가 다르다는 것과 모델에 들어가는 token ID가 다르다는 것은 구분한다.

토큰열이 같은24상황×두 모델=48개는 같은 실행의 기준선 응답을 alias로 재사용한다. 이를 두 번 생성한 것으로 세지 않는다. 다른22상황×두 모델=44개 템플릿 대조는 새 생성한다. 총368개 비교 셀에 대해 예상 실제 generate 호출은320개이며, 중복48개는 provenance와 별도 횟수를 남긴다. 이런 동일 입력 alias는 독립적인 추가 평가 증거가 아니다.

## decoder 해제와 품질 판정

decoder off에서도 schema 조건화 메시지는 그대로다. 이전의 schema 누락 legacy 조건과 다르다. 달라지는 것은 토큰 마스크 logits processor뿐이다. raw JSON·구문·schema·소비자·EOS 결과를 각각 남기고 enum 치환이나 JSON 복구는 하지 않는다.

내용 품질과 앱 사용 가능성을 분리한다. JSON 파싱이 되지만 enum/소비자 계약을 어긴 경우의 원래 spoken_text는 **진단용 내용**으로만 평가할 수 있다. JSON 파싱이 안 되면 raw 출력 자체를 GPT가 읽으며 regex로 발화문을 추출하거나 앱 응답으로 고치지 않는다. 읽을 수 있는 내용이 없는 경우는 unassessable로 별도 표시하고 임의의0점/성공으로 채우지 않는다. 모델의 잘못된 출력을 대화 기억이나 TTS에 추가하지 않는다.

GPT는 모델/실험 조건을 가린 실제 내용을 먼저 읽고, 기존 말투·관련성·자연스러움 및 해당 질문의 자기소개·정직성·문맥·규칙 보호 rubric으로 판정했다. 이후 대응표를 해제해 내용 엄격 통과와 **계약/EOS까지 만족한 앱 사용 가능 엄격 통과**를 따로 집계했다. 같은 상황에서 똑같은 표시 내용은 같은 항목 판정을 받도록 검사했고 통과했다. 모든 원문에 읽을 수 있는 내용이 있어 unassessable은0개였다. raw 형식으로 decoder 해제 조건을 짐작할 수 있으므로 완전한 blind는 아니다. prompt 작성자와 평가자가 같은 GPT라는 한계, 이미 본 질문·고정된 오류 과거 대화·단일 seed라는 한계를 함께 기록한다.

## 실제 구조·품질 결과

각 행의 분모는46상황이다. 내용 엄격 통과는 적용된 GPT rubric이 모두 pass인 경우이며 partial은 통과로 채우지 않았다. 앱 사용 가능 엄격 통과에는 계약과 EOS까지 요구한다. alias48개를 새 생성/독립 표본이라고 보고하지 않는다.

여기서 앱 사용 가능은 Python에서 현재 앱 JSON 소비 계약을 만족한다는 뜻이다. Android에서 해당 checkpoint·NF4/BF16 실행이나 모델 importer를 검증한 결과는 아니다.

### 1. 템플릿: 차이는 실재하지만 교체가 개선책은 아님

22개 다른 입력 상황에서 실제 raw 응답은 원본19개, adapter21개 바뀌었다. spoken_text 문자열은 각각15개·14개 바뀌었다. 그러나 내용 엄격 통과는 기준선6→3,8→6으로 낮아졌다. 단일 턴/과거 없음24상황은 토큰 동등이므로 이 템플릿 변경의 대조 대상 변화가 아니다.

과거 assistant의 빈 think 블록 유무는 실제 요인이지만, 학습 템플릿을 그대로 추론 기본값으로 바꿔야 한다는 결론은 지지되지 않는다. 정답이 없는 이름 경계·역할·정직성 오류도 남았다. 이 결과가 모든 템플릿 또는 multi-turn 학습의 효과를 배제하는 것은 아니다.

### 2. NF4: 출력은 크게 달라지지만 공통 오류의 단독 설명은 아님

전체 BF16에서 raw 응답은 원본45/46·adapter43/46, 비교 가능한 spoken_text는36/46·34/46 바뀌었다. GPT 내용 엄격 통과는 원본6→9로 일부 증가했지만 adapter8→7로 감소했다. 이름/정직성·소유자 혼동·반복 등 공통 문제는 해결되지 않았다. 이46상황·단일 seed·같은 GPT 판정에서의 작은 차이를 일반적인 품질 향상/통계적 우승으로 보고하지 않는다.

실제 파라미터와 레이어를 확인했다. NF4 원본은 BF16 파라미터134개와 uint8 파라미터186개, 전체 BF16 원본은 BF16 파라미터320개였다. 전체 BF16에는 Linear4bit 모듈이0개였고, 두 정밀도 모두 모든 파라미터가 CUDA에 있었으며 학습 가능한 파라미터는0개였다. 같은 adapter의24개 LoRA 파라미터 dtype은 두 조건 모두 FP32로 같았다. NF4+PEFT의 모듈 수는 wrapper를 중복 집계할 수 있으므로 실제 양자화 가중치 개수와 혼동하지 않는다. CPU/disk 대체나 OOM은 없었다.

따라서 NF4가 무관하다고 말하지는 않지만 **NF4를 제거하기만 하면 현재의 낮은 대화 품질이 해결된다**고 단정할 근거는 없다. 이 실험은 양자화 레이어/가중치 및 그 커널의 전체 변경이며 반올림 오차와 개별 커널 효과까지 나눈 결과는 아니다.

### 3. decoder: 내용 파괴의 공통 원인보다 형식 보장의 효과가 뚜렷함

decoder를 해제했을 때 양쪽 모두 literal spoken_text를 파싱할 수 있었던 원본27상황 중 발화 변경은0개, adapter34상황 중 변경은1개였다. 나머지 raw 미구문/문자열 출력도 GPT가 원문 그대로 읽어 판정했다. 미파싱 사례를 조용히 제외한 동일성 수치가 아니며 분모를27/34로 명시했다. 전체 raw JSON의 변경은29/46·13/46이었다.

내용 엄격 통과는6→4,8→7로 낮아졌고 앱 사용 가능 엄격 통과는6→1,8→5로 더 낮아졌다. JSON 제약이 공통 소유자/자기소개/정직성 오류를 주로 만든다는 증거는 얻지 못했다. 현재 앱에는 schema 안내와 생성 제약·소비자 검증을 유지하는 편이 이 실험 결과에 맞는다. decoder off를 배포 기본값으로 채택하지 않는다.
